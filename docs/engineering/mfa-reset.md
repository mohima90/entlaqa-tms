# Lost authenticator app: who resets it, and the ENTLAQA support runbook

A member who lost their phone (or the app on it) cannot pass the authenticator code their organization asks for, and cannot remove the app themselves (that needs a code from it). Someone else removes the app; the member then sets up a new one at their next sign-in, and confirms it from their mailbox like any new app (review H1). Every reset removes **every** authenticator app of the login, **ends every sign-in session** of it (also in Auth), is **audited** and **e-mailed** to the person.

## 1. Who resets what

| The person | Who resets | Where |
|---|---|---|
| A member whose login belongs to **this organization only** | An **Organization Admin** of the organization (not their own app) | User profile → *Sign-in and security* → **Reset authenticator app** («إعادة ضبط تطبيق المصادقة») |
| An Organization Admin, when **another Organization Admin** of the same organization exists | That other Organization Admin | Same |
| The **only** Organization Admin of an organization | **ENTLAQA support** | §2–§4 below |
| A person with an active membership in **more than one organization** | **ENTLAQA support** (one login, one app: an organization may not change what another relies on) | §2–§4 below; the app answers the Organization Admin «ENTLAQA support resets it» |
| Someone who still has the app | Themselves | My profile → *Remove the authenticator app* (with a code from it) |

The in-app reset (first two rows) needs: the Organization Admin role in force; a code from the admin's **own confirmed** authenticator app entered in the **last 15 minutes** (the page asks for it and returns to the profile); a member the admin may manage; a confirmation dialog. The database checks the same again (`private.reset_member_mfa`) and refuses a login that is an active member of another active organization (`other_organization`). Audit: `platform.user.mfa_reset` (entity: the person; no personal data). The member gets the «Authenticator app removed» e-mail.

## 2. Support: before anything — the request and the identity check

A reset by support is a high-value social-engineering target (TM-0003 AB-IAM-07, risk register R-47): "I lost my phone, it's urgent" is exactly what an attacker who has the password says. Do **all** of the following and record each step in the support ticket. If any step fails or feels rushed, **stop and refuse**; the person can always come back.

1. **Open a ticket.** Its id is the **support reference** (3–64 characters: `A–Z a–z 0–9 . _ : -`, e.g. `SUP-1042`). The reference is written into the audit trail, so it must **never** contain a name, e-mail, phone number or any other personal data.
2. **Find the account by the login e-mail on file**, never by details only given in the request (§3, step 1). Note the organizations it belongs to.
3. **Mailbox check.** Send a one-time verification code (8 random digits, generated by support, valid 30 minutes) **from the support mailbox to the login e-mail on file** — not to an address given in the request — and ask the person to read it back during the call in step 4.
4. **Call back** on a phone number held **by the organization** (the person's HR record, or the organization's contact on the customer contract) — never a number given in the request. Ask for the code from step 3.
5. **Confirm with the organization.**
   - For a member of several organizations: an Organization Admin of **at least one** of them confirms the request (call-back to that admin as in step 4).
   - For the only Organization Admin: the organization's **authorized signatory** confirms it, checked against the commercial registration and the signatory documents on the customer contract (the same check as the R-47 recovery runbook).
6. **Second approval.** A second ENTLAQA staff member reviews steps 1–5 in the ticket and approves the reset there (four eyes). Nobody approves their own ticket.

## 3. Support: the reset

Run as the **migration role** — the only role that may call `private.reset_account_mfa` (the web app's, the worker's and the queue's roles are refused):
- hosted staging/production: Supabase dashboard → **SQL Editor** (runs as `postgres`, the migration role);
- self-hosted: `psql` as the installation's migration role over TLS (`PGSSLMODE=verify-full`), as in `infra/docker/README.md` ("Manual operation").

1. The account and its organizations (replace the e-mail; nothing is changed by these reads):

   ```sql
   select u.id, u.email, (select count(*) from auth.mfa_factors f where f.user_id = u.id) as apps
   from auth.users u where u.email = lower('person@example.org');

   select t.slug, t.status, m.status as membership
   from platform.tenant_memberships m join platform.tenants t on t.id = m.tenant_id
   where m.user_id = '<account id>';
   ```

2. The reset — the account id and the ticket reference, nothing else:

   ```sql
   select private.reset_account_mfa('<account id>', 'SUP-1042');
   ```

   It returns how many apps were removed (0 is allowed: the sessions still end). In one transaction it removes every authenticator app of the account in Auth, ends every sign-in session (revocation marker and the Auth session itself), writes `platform.auth.mfa_reset` with `{"by": "support", "reference": "SUP-1042", "apps": n}` into the audit trail of **each** organization of the account, and queues the «Authenticator app removed» e-mail (when an app was removed).

3. Check it:

   ```sql
   select count(*) from auth.mfa_factors where user_id = '<account id>';          -- 0
   select count(*) from auth.sessions where user_id = '<account id>';             -- 0
   select tenant_id, occurred_at from platform.audit_events
   where action = 'platform.auth.mfa_reset' and data ->> 'reference' = 'SUP-1042';  -- one row per organization
   ```

4. Tell the person (on the call or by e-mail to the login address): at the next sign-in they set up a new app and confirm it from the e-mail it sends; if they think someone else knew their password, they set a new one from **Forgot your password?** first. Tell the Organization Admins of the person's organizations that support reset the app (ticket reference only).
5. Close the ticket with the evidence of §2 (who confirmed, when, how) and the result of step 3.

## 4. Never

- Never delete factors or sessions in the Auth tables directly, and never use the Supabase dashboard's *Users → Remove MFA factor*: that skips the audit trail, the e-mail and the end of the sessions.
- Never reset without a ticket, the identity check of §2 and a second approval — not for a colleague, not "just this once".
- Never put personal data into the reference, and never paste the verification code of §2 into the ticket after use.
- Never reset an app for someone who still has it: they remove it themselves in My profile.

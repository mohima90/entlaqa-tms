# ADR 0005 — Background jobs and scheduling (self-hostable)

**Status:** Accepted — PR #9, 30 Sep 2026 · **Date:** 30 Sep 2026 · **Backlog:** T-M1-B05 · **Related:** BRD Appendix H.1; FR-NTF-08, FR-CRT-05, FR-CRT-07/08, FR-SCH-08, FR-LOG-01/02, FR-ASM-05, FR-LMS-05/07/10, FR-IAM-03/04, FR-RPT-02; NFR-PERF-05, NFR-SCAL-03, NFR-AVL-04; TM-0001 F-01, F-03 (TB-9); ADR 0001, ADR 0002 §5–§7 (incl. §6a), ADR 0004, ADR 0006, ADR 0009, ADR 0010

## Context

- R1 needs asynchronous work (event deliveries from ADR 0004, e-mail sending, file scanning, PDF certificates, imports of 10,000 users ≤ 5 min, report exports ≤ 2 min) and **schedules** (reminders, certificate expiry, compliance recalculation, LMS reconciliation).
- The same code must run on Vercel (regional SaaS: serverless functions, no long-running processes) and in containers (sovereign, customer-hosted), with no Vercel-only feature in a critical path (CLAUDE.md, BRD §15).
- Jobs touch tenant data and must respect RLS with a per-tenant system actor (ADR 0002 §7).
- Malware scanning needs a ClamAV daemon (ADR 0006), which cannot run on Vercel — so every production deployment needs at least one container host anyway.

## Options considered

| Option | Runs TypeScript jobs | Self-hostable | Scheduling | Notes |
|---|---|---|---|---|
| `pg_cron` (Supabase Cron) | No (SQL only; HTTP via `pg_net`) | Yes (extension) | Cron in DB | Good trigger, not a job runner; retries/backoff/visibility are ours to build |
| Vercel Cron | Calls an HTTP route | No (Vercel-only) | Per-minute on paid plans (verify plan limits) | Trigger only; function duration limits apply |
| Supabase Edge Functions | Deno, separate runtime | Edge runtime self-hostable | Via pg_cron | Second runtime and toolchain; not in the monorepo build |
| **graphile-worker** | Yes (Node) | Yes (SQL schema, no extension) | Built-in distributed crontab | `add_job` callable from SQL inside transactions; `job_key` dedupe/debounce; named queues for serial execution; LISTEN/NOTIFY for low latency; `runOnce` mode |
| pg-boss | Yes (Node) | Yes | `schedule()` cron | Built-in dead-letter queues and throttling; polling-based; transactional enqueue needs a custom `db` executor (verify) |

## Decision

**graphile-worker is the single job runner and scheduler** for all deployment models (package `platform-jobs`). Its schema `graphile_worker` lives in the application database. pg_cron and Vercel Cron are only **optional triggers** for non-production environments, never the place where job logic lives.

### 1. Runtime modes (same job code, same image)
| Mode | Where | How |
|---|---|---|
| **Daemon** (the only production mode) | Container `worker` (Node 24, same monorepo build as `apps/suite`, different entrypoint) | `run()` with LISTEN/NOTIFY; concurrency per process configurable; **≥ 2 replicas** for availability; graceful shutdown on SIGTERM |
| **Tick** (previews and local development only) | Route handler `POST /api/internal/jobs/tick` | Exists only in builds for preview/local environments, which hold **no production secrets** (synthetic data only). Shared secret compared in **constant time**, route rate-limited, bounded time budget; triggered by Vercel Cron on previews or manually |

- **Production resilience comes from a second worker replica, not from the web tier** (TM-0001 F-03). The web deployment's environment never contains the `app_worker`/`app_queue` credentials or the Supabase service key; privileged credentials exist only in the worker runtime (trust boundary TB-9).
- **Regional SaaS (R1):** web on Vercel `fra1`; ≥ 2 `worker` replicas (plus ClamAV, ADR 0006) on a container host in Frankfurt next to Supabase `eu-central-1` (host to be approved by the PO). The production Vercel project has no tick route and no cron entries.
- **Sovereign / dedicated / customer-hosted:** `worker` Deployment (≥ 2 replicas) in the same cluster (ADR 0010).

> **Amendment (PO decision, 20 Oct 2026) — how hosted passes start while there is no worker host.** GitHub Actions runs the worker one pass at a time (`.github/workflows/jobs.yml`, implementation note T-M2-06a), and GitHub starts its 5-minute schedule late or skips it (20 Oct 2026: about 5 runs in the day), so e-mails, scans and imports waited hours. As in Kawadir ATS (kick after mutating requests with `after()`, plus a per-minute Vercel Cron), **the web app now starts that workflow** (`workflow_dispatch`, GitHub REST API): right after a committed action that queued work (defineAction's central hook — an emitted domain event or `queuesWork: true` — and the public flows that queue account e-mails), and from a **Vercel Cron every minute** (`GET /api/cron/jobs`, `Authorization: Bearer <CRON_SECRET>`). The **worker's keys stay on GitHub**: Vercel holds only the private key of a dedicated **GitHub App** (Actions: read and write, installed on this repository only; corrected 21 Oct 2026 after security review H1 — the first version's personal token acted as the PO's own user and could start every workflow, admin ones included) — no database, queue, Storage or Auth credential; TB-9 holds. **Every other workflow with `workflow_dispatch` refuses a run started or re-run by that App** (`github.triggering_actor` = repository variable `JOBS_KICK_ACTOR`) and any manual start by a `[bot]`; a refused run fails visibly. The cron entry and the route contain **no job logic** (they only ask GitHub), so the decision above — no job logic in Vercel Cron, no tick route — still holds; the line "no cron entries" is amended accordingly. No App settings → no dispatch (self-hosted runs the daemon; nothing changes there). The 5-minute schedule stays as the safety net; the workflow's `concurrency` group keeps one pass running and one waiting, and each web instance dispatches at most once a minute for actions (the cron has its own window). Code: `packages/platform-jobs/src/kick/`; runbook: `docs/engineering/background-jobs.md` §1a. This is a bridge until the worker host (above) is approved; it is not a production mode of its own.

### 2. Database roles and connections
- `app_worker`: login role, member of `authenticated` with **`NOINHERIT`**, **no `BYPASSRLS`**, owns nothing (ADR 0002 §5). Used by job handlers through `withSystemTx`, which does `set local role authenticated` and sets the **system-actor claim set** defined in ADR 0002 §7 (`role: 'system'`, `tenant_id`, job id). `private.current_tenant_id()` accepts system claims **only when `session_user = 'app_worker'`** and the tenant is active or trial (ADR 0002 §6a), so a leaked `app_server` credential cannot impersonate jobs and vice versa.
- `app_queue`: login role that owns the `graphile_worker` schema; **not** a member of `authenticated`; no `BYPASSRLS`; used by the runner itself and the event dispatcher (ADR 0004). It has narrow explicit policies (outbox dispatch columns, `platform.tenants` id/status/timezone) and can read no business table. Worker schema migrations run at deploy time with a direct/session connection (they use session-level advisory locks).
- The worker process therefore holds two pools: `app_queue` (runner, dispatcher) and `app_worker` (handlers). The Supabase service key (Storage operations in ADR 0006) is present only in the worker environment.
- Daemon mode needs a **session** connection (direct or Supavisor session mode) for LISTEN/NOTIFY; handler pools may use the transaction pooler (prepared statements disabled if required — verify).
- No grants on `graphile_worker` to `authenticated`/`anon`; the schema is never exposed through the Data API. It is on the RLS catalog-check allow-list as infrastructure.

### 3. Enqueuing
- Request-path code does **not** enqueue jobs directly. It emits a domain event or a command-style event (e.g., `com.entlaqa.platform.file.uploaded`, `com.entlaqa.platform.export.requested`) through the outbox (ADR 0004); subscribers turn them into jobs. One transactional path, no lost jobs.
- Job payloads contain only IDs (`tenant_id`, entity ids, event id) — never personal data or secrets.
- Deduplication with `job_key` (e.g., `cert-expiry:<tenant>:<date>`); serial execution where needed with named queues (e.g., one queue per LMS connection).

### 4. Tenant execution context
- Every tenant job runs inside `withSystemTx(tenantId, { jobId, task })` with the system-actor claim set of ADR 0002 §7 (validated in the database per §6a), so RLS applies exactly as for users. Audit events and outbox rows written by jobs carry actor type `system` and the task name. `withSystemTx` is importable only from `**/jobs/**` (dependency-cruiser rule) and only works under the `app_worker` login.
- Jobs check the tenant is `active`/`trial` and the feature is licensed/enabled (FR-ADM-13, SUB-01) before doing work.
- Cross-tenant work (fan-out over tenants, housekeeping) uses `app_queue` with explicit narrow policies (e.g., read `platform.tenants.id, status, default_timezone`) or the admin client — the latter only in `**/jobs/**`, audited (ADR 0002 §7).

### 5. Scheduling model
- Global crontab entries (UTC) run **fan-out** tasks that enumerate eligible tenants and enqueue one job per tenant with a window `job_key`, so every tenant job is idempotent per window and can be retried safely.
- Tenant-local times (digests at 07:00 local, quiet hours) are evaluated inside the per-tenant job using the tenant/branch timezone and working calendar (ADR 0007).
- Scan-based reminders ("what is due in this window?") are preferred over per-item future jobs, so reschedules and cancellations need no job cleanup; each reminder is recorded (`platform.scheduled_dispatches` unique on `(tenant, rule, subject, offset)`) to prevent duplicates.

### 7. Failure handling
Exponential backoff (graphile-worker default; verify formula), `max_attempts` per task, permanent failures recorded in `platform.job_failures` (sanitized) and alerted; long jobs checkpoint progress (imports in batches of 500 rows) so a retry resumes. Job-level timeouts are enforced by the task wrapper.

## Consequences

**Positive:** one runner, one scheduler, one set of semantics everywhere; transactional enqueue via the outbox; per-tenant idempotent schedules; no vendor lock-in.

**Negative / costs:** regional SaaS needs a small container host besides Vercel with at least two worker replicas (also required by ClamAV); graphile-worker's crontab and backoff semantics must be learned and tested; LISTEN requires session connections (connection budget planning).

## Security impact
Privileged credentials (`app_worker`, `app_queue`, service key, provider keys) exist only in the worker runtime (TM-0001 F-03, TB-9); no tick route in production; system claims only constructed in `**/jobs/**` and accepted by the database only under `app_worker` (F-01); no PII in job payloads; admin-client use limited and audited; job failures sanitized before storage/logging.

## Sovereign deployment impact
graphile-worker needs only PostgreSQL and Node — both in-country. No cloud scheduler required.

## Suite impact
Each module registers tasks and crontab entries in its `jobs/` folder with namespaced names (`tms.*`, `core_hr.*`); the platform runner loads all licensed modules' tasks.

## Verification
1. Integration tests run tasks against a real PostgreSQL (local Supabase) with two tenants; RLS isolation holds under `withSystemTx`.
2. Idempotency tests: running a scheduled task twice in the same window produces no duplicate reminders/notifications.
3. Self-hosted smoke test (ADR 0010): daemon mode processes an event, a scan job and a scheduled task; tick mode verified only on the Vercel preview.
6. Configuration tests: the production web environment contains no worker/service credentials and no tick route; system claims set under `app_server` read zero rows (ADR 0002 §6a test 3a); killing one worker replica does not stop processing.
4. Import performance test: 10,000 users ≤ 5 min (NFR-PERF-05).
5. Alerts on queue depth, oldest runnable job age and permanent failures (ADR 0009).

## Implementation notes

### T-M2-06a (6 Oct 2026): runner, worker app and staging
- **Package `platform-jobs`** (`src/jobs/` only, importable from job code and `apps/worker`): graphile-worker 0.18 runner, the event dispatcher and delivery tasks (ADR 0004), the subscriber registry, the event listener (daemon mode). A dependency rule (`queue-driver-only-in-platform-jobs`) keeps graphile-worker and its `pg` driver inside that folder. The queue connection URL may carry TLS settings only: `pg` lets other parameters (`?host=`, `?user=`) override what the role and TLS checks look at.
- **`apps/worker`** bundles everything into one file (esbuild) and runs `daemon` or `once` (`runOnce` after queueing a dispatch; the run fails when events wait for more than 10 minutes). Its configuration is checked before any connection: login roles `app_queue` / `app_worker`, TLS verify-full for remote hosts. In daemon mode the process handles SIGTERM/SIGINT itself (graphile-worker's handler would re-raise the signal and skip clean-up): running jobs finish, connections close, exit 0. Image `infra/docker/worker.Dockerfile` (distroless, non-root); the self-hosted stack runs two replicas with a 60-second stop grace period.
- **`app_queue` privileges (after the independent security review):** no privilege on the database itself and nothing owned outside `graphile_worker`. graphile-worker 0.18 installs its tables at start-up without advisory locks; it runs `create schema if not exists` (which needs CREATE on the database) only when its migrations table is missing, so the migration creates that bootstrap table owned by `app_queue`. With CREATE, `app_queue` could have added schemas named after other roles and captured their unqualified names. Catalog and deployment checks enforce both rules.
- **Operating the queue:** everything in `graphile_worker` belongs to `app_queue`, which can replace it, so queue commands (inspecting jobs, rescheduling, unlocking) run only in a session logged in as `app_queue`, never as `postgres` or another more powerful role (runbook §5).
- **Job errors:** tasks rethrow failures as `JobError` (class name, stable code, stack locations): graphile-worker logs the message and stores it in `jobs.last_error`, and messages may carry personal data (ADR 0009 §2).
- **Tenant checks (§4):** deliveries skip organizations that are not active (`private.current_tenant_id()` resolves to no tenant), with a warning, instead of failing until the attempts run out.
- **Staging (deviation from §1, tick mode not built):** the web app cannot reach job code at all (dependency rules), so there is no tick route. Until the production container host is approved, staging runs one worker pass every 5 minutes as a scheduled GitHub Actions workflow (**Jobs (staging)**), with its own GitHub environment `staging-jobs` that holds only the `app_queue` and `app_worker` credentials — the web deployment still holds none (TB-9). The repository is public: run logs contain no payloads or personal data. Runbook: `docs/engineering/background-jobs.md`.
- **Not yet built:** `platform.job_failures`, alerts and dashboards (§7, ADR 0009), the R1 schedules of §6 (with their features), cross-tenant fan-out policies for `app_queue` (§4), housekeeping of jobs left locked by a dead worker (they end as failed rows after the 4-hour lock expiry).

### T-M2-17 (8 Oct 2026): platform tasks — work without a tenant
- Some work belongs to no tenant until the worker resolves one: a password-reset request comes from a visitor without session or organization, so it cannot be an outbox event (ADR 0004: every event has a tenant). A **platform task** (`PlatformTask`, `packages/platform-jobs/src/jobs/platform-tasks.ts`) is a payload-free job that drains such a platform-level queue in the database through its own narrow SECURITY DEFINER functions (first: `platform.account_mail`, `private.account_mail_requests`). One job per task is pending at most (job key = its name); it is queued on every worker wake-up next to the event dispatch (the queue's insert trigger notifies `jadarat_events`), every minute (cron), and in each round of a one-pass run — so in daemon mode it runs within seconds. Each pass handles a bounded batch and queues the next pass when work is left; per-item retries are bookkeeping in the queue table (lease, attempts, back-off), not job retries.
- **Platform transactions:** `withPlatformTx` (`@jadarat/platform-db/jobs`) sets system-actor claims **without** a tenant under the `app_worker` login: RLS shows no tenant data (`private.current_tenant_id()` is NULL); only definer functions that check for a job under `app_worker` answer. Tenant work then runs in `withSystemTx` for the resolved tenant as usual. `app_queue` gains no privilege (it never reads the platform queue).
- The task's dependencies (its transactions, the Auth admin API, settings) are bound by the worker app when it creates the task (`apps/worker/src/platform-tasks.ts`).

### T-M2-12 (10 Oct 2026): the user import — a long platform task with leases and checkpoints
- The bulk user import (FR-IAM-04, NFR-PERF-05) is the platform task `platform.user_imports` (`packages/platform-import/src/jobs`), not one job per import: imports of every organization are claimed through `private.claim_user_import_work()` (owner `user_import_guard`, the pattern of `claim_file_scan`; the import waiting longest goes first, so imports take turns) with a **15-minute lease** per import, so one worker at a time works on an import and a dead worker's import is picked up again when its lease ends. Each step runs in the import's tenant transactions (`withSystemTx`) that check the lease; the worker's domain events (`user_import.mapped`, `.confirmed`, `.undo_requested`, `.invitations_scheduled`) wake it.
- **§7 checkpoints as decided:** rows are written in **batches of 500 per transaction**, each committing its progress (`rows_done`), so a restart continues after the last batch; a pass hands over after 4 minutes (the next pass is queued at once). A failed step is retried after 2ⁿ minutes (at most an hour) and the import ends `failed` after 6 failures — bookkeeping in `platform.user_imports`, not job retries (as for platform tasks, T-M2-17).
- **One running import per organization** (unique index) bounds the load per tenant (TM-0003 T-IAM-34). Runbook: `docs/engineering/user-import.md`.
- **A platform-wide rate in the database** (security review M2): the run's invitations are released by the same task, one per transaction, each taking a slot of a single-row send clock (`private.invitation_send_clock`, slot function owned by `user_import_guard`): the row lock serialises the workers of every organization, a rolled-back release returns its slot, and overdue work is spaced out instead of bursting. A turn sends at most 30 of one import and hands over; a per-organization daily number (counted on `released_at`) defers the rest to the next UTC day. The pattern suits any shared external limit (e.g. later SMS).
- **Leases renewed, lost leases counted** (security review H1): every transaction of a step renews its lease and a long read renews it as rows go; a step that outlives its lease counts as a failure with the back-off, so no step can be claimed forever. A run ends even when its last write (the error report) cannot be done (security review M1: stored in a savepoint, retried with the step, then skipped with a code).
- **Not yet verified:** the NFR-PERF-05 target (10,000 rows ≤ 5 minutes) on the production worker host; staging's 5-minute passes make an import take several passes.

### Web-app kick (20 Oct 2026, PO decision; amendment to §1)
- **Dispatcher** `@jadarat/platform-jobs/kick` (`src/kick/dispatch.ts`, server-only, outside `src/jobs/`, so the web app may import it and still reaches no job code), **as a GitHub App** (amended 21 Oct 2026, security review H1): an RS256 App JWT signed with `node:crypto` (`iat` now − 60 s, `exp` now + 9 min, `iss` = `JOBS_DISPATCH_APP_ID`) is exchanged at `POST https://api.github.com/app/installations/{JOBS_DISPATCH_INSTALLATION_ID}/access_tokens` for an installation token narrowed to `{"repositories":[<repo>],"permissions":{"actions":"write"}}`, cached in memory until 5 minutes before its expiry; then `POST https://api.github.com/repos/{JOBS_DISPATCH_REPO}/actions/workflows/{JOBS_DISPATCH_WORKFLOW|jobs.yml}/dispatches` with `{ "ref": JOBS_DISPATCH_REF|main }`. 5-second timeout per call and `redirect: error`; settings checked against strict patterns (the origin is fixed — no SSRF through configuration); one dispatch a minute per server instance for actions, a separate 30-second window for the cron; never throws; logs outcome and HTTP status, never the key, the JWT, the token or a response body. The private key (`JOBS_DISPATCH_APP_PRIVATE_KEY`) is the only secret; rotation: background-jobs.md §1a.
- **Workflow guard:** `ci.yml`, `codeql.yml`, `db-deploy.yml`, `db-deploy-auto.yml`, `platform-admin.yml`, `tenant-provision.yml`, `selfhosted-nightly.yml` and `uptime.yml` refuse a run whose `github.triggering_actor` equals `vars.JOBS_KICK_ACTOR` (any event — re-runs included) or, for `workflow_dispatch`, ends with `[bot]` (job-level `if` on every job that does work, plus a failing "Refuse a start by the worker-kick app or another bot" job; CI gates and CodeQL fail rather than skip). Jobs lets the App run the production pass only. What the App can still do with Actions write: start/cancel/re-run Jobs, disable or enable workflows (e.g. CI — a denial of service), delete runs and logs.
- **After the commit:** defineAction asks `runtime.requestWorkerPass` once the transaction committed, when the committed attempt emitted an event (platform-db `emitEvent` marks its transaction), marked it with `noteWorkQueued` (a Branding save whose new image is left to the worker), or the action declares `queuesWork: true` (test e-mail, own password change). Work queued by SQL functions or triggers on their own, in another transaction, or by jobs is not detected (review L2) — such actions declare `queuesWork`; a missed kick only waits for the next scheduled pass. `@jadarat/platform-jobs/kick/next` schedules the dispatch with Next's `after()`, so it never delays or changes the answer. Public flows wrap their account-mail queue functions (`kicksWorker`, platform-identity `auth-next.ts`).
- **Cron:** `apps/suite/vercel.json` `crons: [{ path: /api/cron/jobs, schedule: "* * * * *" }]` (Vercel Pro, PO 20 Oct 2026); the route refuses every call without `Authorization: Bearer <CRON_SECRET>` (≥ 16 characters, both sides trimmed alike, constant-time compare; no CRON_SECRET on the server → always 401; a wrong bearer is logged without values, at most every 10 minutes per instance).

### E-mail credentials in the web tier for the sign-in code (23 Oct 2026, PO decision; amendment to §1 and the "web deployment holds no worker credentials" rule, TB-9)
- **Decision.** The one-time sign-in code must reach the person **immediately** (PO, 23 Oct 2026: "the way Kawadir sends them straight from Vercel"), which a queue and a worker pass cannot promise. Supabase Auth's Send Email hook therefore calls a route of the web app (`apps/suite/src/app/api/auth/send-email`), which sends that one e-mail itself. Everything else still goes through the delivery log and the worker (ADR 0008).
- **What the web tier now holds:** `SEND_EMAIL_HOOK_SECRET` (verifies Auth's signature) and **`EMAIL_CREDENTIALS_KEY`** (the same value as the worker's — it opens the e-mail provider secrets saved in the product), plus, for self-hosted operators only, the installation sender's variables. It still holds **no** database credentials of the worker (`app_queue`, `app_worker`), **no** Auth secret key and **no** GitHub App key beyond the kick's.
- **How the boundary is kept (security re-review M-B, 23 Oct 2026).** The route imports a separate entry point, `@jadarat/platform-notifications/inline` (the sender rule and the transports; no queue, no job code, no `app_worker` connection). That sender code used to live under `jobs/`, where the rule `admin-jobs-folders-are-private` kept it away from the request path; it now lives in `packages/platform-notifications/src/sending/`, and the dependency-cruiser rule **`email-sending-code-is-private`** restores the protection: only the notifications package itself (the worker's `jobs/`), `apps/worker`, the hook adapter (`platform-identity` `auth-next.ts` / `auth-email-hook.ts`) and the hook route may import `sending/` or `src/inline.ts` — anything else in the web app fails CI (fixture test in `scripts/dependency-rules.test.mjs`); every file there starts with `import 'server-only'`. The sender settings are read by `SECURITY DEFINER` functions callable by the web tier's login role only, and the sealed secrets are reachable **only inside `private.auth_mail_issue`**, which stores a sign-in code for a real, usable account in the same call (`private.auth_mail_route` is internal: not executable by the web tier on its own). A database-side proof that the caller is the hook is not possible without a secret the database would have to hold as well, so a compromised web tier — which already holds the key — can still reach it through that function; the function limits the damage to accounts that exist and replaces their live code. The code is rendered in memory, sent, and never written to the delivery log.
- **Accepted consequence.** A compromise of the web tier can now read the organizations' e-mail provider secrets, which only the worker could before. **Accepted by the PO on 23 Oct 2026** (`docs/delivery/STATUS.md` §2 «Decisions Log», row of 23 Oct 2026 «WP-ADM-05: launch now, e-mails at once…», point 2: the e-mail sending keys go into Vercel). Mitigations: the secrets stay sealed at rest and revocable at the provider; the hook accepts only Auth's signature and acts once per webhook id; the hook sends at most 10 codes per 15 minutes and 40 a day per account; the sender code is reachable only from the hook (above); the key never reaches a log, a response or a browser (`NEXT_PUBLIC_` is not used).


### Every e-mail immediately: the web app sends, the worker is the safety net (23 Oct 2026, PO decision; amendment to §1 and to the sign-in-code section above)
- **Decision.** "Every e-mail arrives immediately" (PO, 23 Oct 2026), with the organization's sender or the platform's. After the action commits, the web app sends the message itself (`after()`), with `@jadarat/platform-notifications/inline` (the same `sending/` code as the worker). The queue (`platform.message_deliveries`), the worker sender, the kick and the minute cron are unchanged and remain the **safety net**: nothing is lost if the function dies or the provider is down.
- **One message, one sender.** The web action queues the delivery in its own transaction with a `source_key` and the SHA-256 of a 32-byte request secret; the claim (status `sending`, `updated_at`, 300 s) is the **same lease** the worker uses, so whoever claims first sends and the other sees `busy`; the provider call carries the delivery id as idempotency key. The worker's mailers skip a message whose `source_key` is already queued; an unfinished inline delivery (≥ 60 s old, or its lease ran out) is re-queued once an hour at most by the `platform.email_inline_rescue` task and sent by the normal sender.
- **Database boundary.** New role `inline_mail_guard` (NOLOGIN, NOINHERIT, NOBYPASSRLS) owns narrow SECURITY DEFINER functions (`inline_mail_queue`, `inline_mail_claim`, `inline_mail_finish`, `inline_email_test_claim`, `inline_email_test_finish`, `inline_mail_tenants_to_rescue`); it has column grants and policies only on what they touch. Queueing authorizes per kind (invitation: the caller may manage that pending invitation and the address is the invitation's); claiming needs the secret, not claims; the sealed sender settings are returned only with a successful claim. pgTAP `99_inline_mail_*` covers cross-tenant, wrong-secret, replay, lease and role-ownership cases.
- **Kinds built (23 Oct 2026, same day):** invitations (create, «Invite another», resend), the test e-mail on both e-mail settings pages, the sign-in code (earlier amendment) - and the **account e-mails**: the password reset, «password changed», the authenticator set-up code and removal, the security-policy and sign-in-unlock notices, an admin's authenticator reset, «account locked» and «wrong codes after your password». Only the security digest and the worker-made e-mails (import finished, invitations released by an import) stay on the worker, which makes them itself.
- **Account notices - the existing request queue is the safety net.** The action queues its account e-mail request as before and, in the same transaction, tags it with the hash of a request secret (`private.inline_account_mail_tag`, only requests created by that transaction); the worker leaves a tagged request alone for two minutes. After the response the web app claims it with the secret - the worker's own lease body (`private.account_mail_claim_core`), now one function for both - applies the worker's caps (`account-mail-compose.ts`, one pure module for both), writes the e-mail and queues the delivery AND removes the request in one step; the delivery is then sent under the shared lease. Authorization: the recipient, organization and person are resolved by the database at the claim and stored on the request (the web app cannot name another address); the template must be the kind's own and the platform-only variant is required for an account of several organizations or a platform role (M1 kept in the database, not only in the web app); the set-up code and link hashes are stored in the same step that queues the delivery. `inline_mail_guard` inserts the delivery (it already may), `account_mail_guard` keeps its four read columns of the delivery log and no write, `tenant_guard` owns three small authenticator helpers that only `account_mail_guard` can call. pgTAP `99_inline_account_mail_owner.sql`.
- **Password reset without the Auth secret key (the proposal above, approved by the PO 23 Oct 2026 and built).** With the Send Email hook on, `PASSWORD_RESET_DELIVERY=auth` asks Auth for a recovery link as before; Auth creates the token and the hook (type `recovery`) e-mails the same link the reset page has always taken (`/{locale}/reset-password#token_hash=...&type=recovery`, the token in the fragment, 60 minutes). No sealing is needed: the link carries Auth's token hash exactly as the worker's did, and no Auth admin key enters the web tier. The hook counts what it sends per account (5 in 15 minutes, 20 a day; own buckets), queues the e-mail as a delivery (the database: the account's own address, the reset's own template, 5 an hour per person, one per webhook) and sends it after answering Auth; every outcome that is not a failure of ours answers success, so the answer does not tell whether an account exists. Residual: the answer time of Auth's public `/recover` for a known address is a database write instead of an SMTP send (a few milliseconds' difference). `worker` mode stays for a deployment whose worker holds the Auth key.
- **Accepted consequence.** The web tier already holds `EMAIL_CREDENTIALS_KEY` (sign-in code decision); the account e-mails use the same key and add no new variable. A compromise of the web tier can read the saved provider secrets and can queue a reset e-mail with arbitrary content to an account's own address (5 an hour per person) - accepted by the PO on 23 Oct 2026 (STATUS §2).

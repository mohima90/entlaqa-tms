## 1. How a message travels

1. A notification subscriber (a job, system claims) calls `queueEmail(tx, { template, locale, to, variables })` in its tenant transaction. The template is rendered in **both languages** — the primary one first with the action button, the other below with a plain link (approved invitation e-mail, screen 7) — and stored in `platform.message_deliveries` with the address, plus an event `com.entlaqa.platform.email.queued`.
2. The worker's e-mail sender (`notifications.email`, an *effect* subscriber) applies the **sender rule** (Kawadir): the organization's own provider when configured **and enabled** (enabled needs a test that went out) → else the **platform sender** once verified by its test e-mail, sent with the **organization's brand name** as display name → else, only while no platform sender was ever saved, the installation sender from the worker's environment. It claims the delivery, sends it with the **delivery id as idempotency key** (Resend returns the first result for a repeated request within 24 hours; over SMTP it becomes the `Message-ID`; SendGrid, Mailgun and Graph have none), and records the outcome with the provider and whose sender it was (`message_deliveries.sender`). **No automatic fallback**: an organization's provider that fails keeps failing as the organization's (shown on its Email integration page).
3. Once a delivery is final — `sent`, `failed` or `suppressed` — its content and plain address are removed; the log keeps the template, language, masked address (`n***@example.com`), provider and its message id, status, attempts and error code (12 months, housekeeping later).
4. A temporary failure (provider down, network) puts the delivery back to `queued` and the job retries with back-off for about **3.5 hours** (10 attempts); a refusal that a retry cannot fix (invalid address, rejected message) or the last attempt records `failed`. Resend rate limits are waited out in place first (Retry-After, at most 10 s, twice). A wrong or revoked API key, or a sender outside the verified domain, counts as temporary, so fixing it within that time lets the waiting messages go out (a missing key stops the worker at start-up with a configuration error).
5. **No sender ready** (none verified yet, or saved secrets that cannot be opened — e.g. after a new `EMAIL_CREDENTIALS_KEY`): the delivery **waits** in the queue (`queued`, error code `NO_SENDER` / `CREDENTIALS_UNAVAILABLE`, content kept) and its job ends — nothing is lost. The Super Admin page warns with the number waiting; the organization's page shows its own count. The worker's resume task (`platform.email_resume`, every pass) queues them again as soon as the organization has a sender ready. A message waiting more than **7 days** for a sender becomes `failed` (`SENDER_WAIT_EXPIRED`: an invitation's code has expired by then).
6. A suspended or closed organization's waiting messages are not sent: their send job discards them (`suppressed`, `TENANT_INACTIVE`, content removed). If the sender's last attempt fails on the database itself it still tries to record `failed` (`DELIVERY_ERROR`); a message left waiting even then keeps its content until the stale-delivery sweeper removes it: the housekeeping task (`platform.email_housekeeping`, T-M2-48, at most every 10 minutes) turns a message waiting more than a day (not for a sender) into `failed` (`STALE`, content removed) and deletes final rows older than **12 months** (BR-NTF-2).

Only jobs (system claims) can read or write deliveries, and the sender acts only on events written by a job; logs and the queue carry codes, never addresses or content.

## 1b. Sent the moment the action commits (WP-ADM-05 follow-up, PO 23 Oct 2026) — the worker is the safety net

**Decision (PO, 23 Oct 2026):** every e-mail arrives immediately, with the organization's sender or the platform's - not after a worker pass. The web app sends it itself, right after the response (`after()`), with the same sender code the worker uses (`packages/platform-notifications/src/sending/`). The queue and the worker stay: if the web app cannot send (no key, provider down, function stopped), the worker sends it later, once.

| Message | How it goes out |
|---|---|
| Invitation (create, **Invite another**, resend) | **Immediate** from the web app |
| Test e-mail on **Platform settings → Email** («Save and send test») and **Settings → Email integration** («Send test e-mail») | **Immediate** from the web app |
| Sign-in code (WP-ADM-05) | Immediate (Send Email Hook route, ADR 0005) - unchanged |
| **Password reset** («forgot password») | **Immediate** from the web app, through Auth's Send Email hook (type `recovery`), no Auth admin key in Vercel (§1c) |
| «Password changed» (My profile and after a reset), authenticator set-up code («send again» too) and removal, security-policy change and sign-in unlock notices, an admin's authenticator reset, «account locked», «wrong codes after your password» | **Immediate** from the web app (§1c) |
| The security digest, «import finished», invitations released by an import | **Worker** (the digest and the import are made by the worker itself; it sends them within its own pass) |

**The steps**

1. **Queue (in the action's transaction).** After the invitation (or test) is saved, `queueInvitationEmailInline` renders the e-mail in the web app and calls `private.inline_mail_queue(...)` in a savepoint. The function checks that the caller may manage that invitation (it asks the same authority function the invitation screens use), that the invitation is pending, and that the address is the invitation's; it writes the delivery as `queued` with a `source_key` (`invitation:<id>:<send count>`) and the **SHA-256 of a request secret** (32 random bytes). The web app keeps the secret in memory only. A failure here never fails the action: no delivery is queued and the worker's own invitation mailer queues it as before.
2. **Send (after the response).** `after()` calls `sendInlineDelivery(id, secret)`: `private.inline_mail_claim` takes the **shared lease** (status `sending`, `updated_at` = the lease start, 300 seconds - the same lease the worker's sender uses) only for the holder of the secret, and returns the sender settings with the claim (never without it). The sender rule runs (`fromRow`, platform-only for account-opening templates), the provider is called with the **delivery id as idempotency key**, and `private.inline_mail_finish` records `sent` / `failed` (content, address and secret hash removed) or sends it back to `queued` with the reason (temporary failure, `NO_SENDER`).
3. **Worker side, no double send.** The worker's invitation mailer skips an invitation whose inline delivery exists (`inlineDeliveryExists`, by `source_key`). A delivery the web app queued but never finished (function stopped) is re-queued by the rescue task `platform.email_inline_rescue` once it is 60 seconds old - or immediately when its lease ran out - and the normal worker sender then sends it (same idempotency key, same lease: whoever claims first sends; the other sees `busy`). A delivery waiting for a sender (`NO_SENDER`) is left to the resume task. Rescue is attempted at most once an hour per delivery (`rescued_at`).
4. **Test e-mails.** The action claims the test in its own transaction (`private.inline_email_test_claim`: Super Admin for the platform sender, the organization's admin for its provider; the same 3-claim limit and lease as the worker's test task; keeps the SHA-256 of a request secret), then sends it after the response and records the outcome with `private.inline_email_test_finish(secret, version, ...)`, which verifies only the settings version it tested (audited). A test nobody finishes is claimed by the worker task after its lease.

**What the web app can and cannot do in the database.** It uses no new login: the functions run as the new role `inline_mail_guard` (SECURITY DEFINER, `NOLOGIN`, `NOBYPASSRLS`, column grants only on the delivery, invitation, person, tenant, membership and custom-role columns it needs) and are granted to `authenticated`/`app_server` only. `queue` and `test_claim` need the caller's verified claims; `claim` and `finish` need **no claims** but need the **secret** - so a request can claim only the message its own transaction queued, never another one (tenant isolation, pgTAP `99_inline_mail_*`). The sender settings (sealed secrets) leave the database only together with a successful claim.

**Rules kept.** Accounts in more than one organization, or with a platform role, still get the platform sender only for account-security e-mails (`PLATFORM_SENDER_TEMPLATES`, applied in the inline path as in the worker's). The one-minute and daily caps of the worker's mailers stay in the worker.

**Gating and set-up.** Inline sending is on only when the web app has `EMAIL_CREDENTIALS_KEY` (already added for the sign-in code; **secret**, the same value as the worker's) or an installation sender (`EMAIL_PROVIDER` not `none`, self-hosted). `APP_BASE_URL` (**config**, already set) builds the links. **No new variable.** Without them the web app queues nothing inline and the worker does everything as in §1.

**What stays on the worker, and why.** The security digest and «import finished» / invitations released by an import are made by the worker itself, which sends them within its own pass. Password reset **through the worker** (`PASSWORD_RESET_DELIVERY=worker`) stays possible for a deployment whose worker holds the Auth secret key; hosted production uses the hook (§1c).

## 1c. Account e-mails sent at once (WP-ADM-05 follow-up, PO 23 Oct 2026) — password reset, notices, authenticator codes

**The account e-mail queue stays the safety net.** An action queues its account e-mail request exactly as before (`private.account_mail_requests`: password changed, authenticator set-up / removal, policy change, unlock, account locked, wrong codes) and, **in the same transaction**, *tags* what it queued with the SHA-256 of a secret only that web request holds (`private.inline_account_mail_tag`; only requests created by that very transaction, `created_txid`). The tag moves the request's `not_before` two minutes ahead so the worker leaves it alone for a moment. After the response (`after()`) the web app:

1. **claims** the request with the secret (`inline_account_mail_claim`): the SAME SQL body as the worker's lease (`private.account_mail_claim_core`: account, banned, organization and language, over the daily ceiling -> held for the digest), with a two-minute lease; the answer carries the organization's names, the counts behind the caps and whether the platform sender is required (several organizations or a platform role);
2. applies the worker's **caps** (`account-mail-compose.ts`, one module for both: hourly cap per person, security notices never dropped, one «account locked» e-mail per person a day and 50 an hour per organization, one «wrong codes» notice per pause);
3. **writes** the e-mail with the worker's wording and **queues the delivery and removes the request in one step** (`inline_account_mail_queue`; the address, organization and person are the ones the claim resolved, the template is the kind's own - the platform-only variant is REQUIRED for the authenticator set-up code of an account of several organizations or a platform role; the set-up code's and link's hashes are stored in the same step);
4. **sends** it under the lease it shares with the worker's sender (`sendInlineDelivery`, delivery id as idempotency key).

Whatever fails, the worker finishes it: an untouched request is the worker's after two minutes, a claimed one when its lease ends, an unfinished delivery by the inline rescue task (§1b); the delivery key `account:<request>` is unique, so a message goes out once. If the web app has no e-mail credentials (§1b) nothing is tagged and the worker does everything as before.

**Where it is called.** Signed-in actions tag inside their own transaction: My profile password change, the authenticator set-up («send again» too) and removal (`auth-next.ts`), and - through `defineAction`'s `queuesAccountMail` (runtime hooks `tagInlineAccountMail` / `sendInlineAccountMail`, after the commit) - the security-policy change notice to every Organization Admin, the sign-in unlock notice and an admin's authenticator reset. The public flows tag in the request function's own transaction (`inline: true`): «account locked» (the typed address; the database decides whether an account exists and sends nothing otherwise), «wrong codes after your password» and the «password changed» notice after a completed reset. The answer to the visitor is sent BEFORE `after()` runs and is constant, so the immediate e-mail adds no timing signal and no enumeration.

**Password reset (type `recovery`).** With Auth's Send Email hook on, `PASSWORD_RESET_DELIVERY=auth` (the default; `hook` internally) asks Auth for a recovery link as before (`resetPasswordForEmail` after the application limiter). Auth creates the token and calls the hook with its `token_hash`; the hook (`auth-email-hook.ts`): verifies the signature, acts once per webhook id (replays ignored), counts what it e-mails per account (**5 in 15 minutes and 20 a day**, own buckets `password_reset.hook_send[_daily]`), reads the account's facts (`inline_recovery_facts`: address, organization, language, sender rule, authenticator app), checks the address is Auth's, writes the link `/{ar|en}/reset-password#token_hash=...&type=recovery[&mfa=1]` (the token in the fragment, the page and its completion unchanged, valid 60 minutes - Auth's `otp_exp`), queues it as a delivery (`inline_recovery_queue`: only the account's own address, the reset's own template - platform-only variant where required -, **at most 5 an hour per person**, one delivery per webhook) and answers Auth with success; the send itself runs after the answer (`after()`). Every outcome that is not a failure of ours (no usable account, over a limit, a repeated call) is a success that tells nothing. No Auth admin key anywhere in the web tier. The «password changed» notice after the reset is queued after the reset completes (the database requires OUR reset e-mail to that account within 65 minutes, the platform-only variant included - fixed in migration 20261026120000 - and its link used).

**Residuals.** (1) The hook's answer time for an existing account is a database write, not a send: a visitor who calls Auth's public `/recover` directly sees a few milliseconds of difference between a known and an unknown address (before: Auth's own SMTP send). (2) A compromised web tier can queue a reset e-mail with arbitrary content to an account's own address (5 an hour per person) - it can already send through the organizations' sealed providers (ADR 0005, accepted 23 Oct 2026). (3) A hook failure on the database (500) tells that an account exists; it needs a database outage.

## 1a. Provider secrets (WP-ADM-01) — sealed for the worker, never readable by the web app (since 23 Oct 2026 the web app also holds the key for immediate sending, §1b)

- The worker derives an X25519 key pair from its **secret** `EMAIL_CREDENTIALS_KEY` (HKDF-SHA256; at least 32 characters) and, at every pass, publishes the **public** key in the database (`private.email_credentials_key`, with a 12-character key id).
- When a Super Admin or an Organization Admin saves a provider, the web app's server seals the secret fields (API key, SMTP password, Microsoft client secret) with that public key: a **sealed box** — a fresh ephemeral X25519 key, ECDH, HKDF-SHA256, AES-256-GCM with a random nonce, the scope (`platform` or the organization's id) and the provider bound as additional data — and stores `v1.<key id>.<payload>`. Until 23 Oct 2026 Vercel (the web app) held **no** key and could never open a saved secret; with immediate sending it holds `EMAIL_CREDENTIALS_KEY` (accepted by the PO, ADR 0005) and opens them only to send a message it claimed (§1b); nothing returns it to any page, log or audit record. Non-secret options (SMTP host/port/user, Mailgun domain/region, Microsoft tenant and client ids) are stored in clear and shown back.
- Only the worker opens them, for the scope they were sealed for (another organization's value does not open). The settings tables are in schema `private`, reachable only through `email_guard`'s reviewed functions (pgTAP `99_email_*`).
- **Without `EMAIL_CREDENTIALS_KEY`** nothing else breaks: no key is published, the pages say e-mail sending is not set up and refuse to save secrets; messages wait. **A new value** = a new key: saved secrets can no longer be opened (`CREDENTIALS_KEY_CHANGED`) — the pages ask for them again and messages wait until then. Keep the value in a password manager; never in chat.
- An SMTP relay set in the product must be on the public internet and use a submission port — 465, 587 or 2525, not 25 (resolved before every send; private, loopback, link-local and IPv4-embedding IPv6 addresses such as NAT64 and 6to4 are refused — `SMTP_HOST_NOT_ALLOWED`); TLS is always required. This holds for every organization's relay and for the platform sender's, unless the operator of a self-hosted installation sets `EMAIL_PLATFORM_SMTP_ALLOW_PRIVATE=true` (internal relay, any port).
- An SMTP password is bound to its server: it is sealed with `host:port` as additional data, and the database keeps a saved password only while host, port and encryption stay the same — another server means typing the password again.
- Every SMTP send has a hard **60-second deadline**; past it the connection is closed and the send fails with `TIMEOUT` (temporary). A server that answers slowly forever cannot hold the worker.
- **Test e-mails** (security review): at most one a minute per sender (every platform save sends one) and 20 a day per organization (`RATE_LIMITED`); the worker claims them one at a time within a 90-second budget per pass; a test claimed 3 times without an outcome fails with `TIMEOUT`; a test still unsent after 7 days (e.g. of a suspended organization) fails with `TEST_EXPIRED` and its recipient is removed.
- Click and open tracking are switched off for SendGrid and Mailgun (invitation links carry codes). Microsoft 365 sends the HTML version only (Graph's JSON sendMail has one body).

Self-hosted stack: `http://localhost:3200` |
| `SUPABASE_URL` / `SUPABASE_SECRET_KEY` | The Auth admin API for password-reset links (T-M2-17): the project's API origin and a secret key (`sb_secret_…`; self-hosted: the service_role token of `gen-secrets.sh`). Check any deployment's settings with `node apps/worker/dist/main.mjs test-email` (one sample invitation, marked `[TEST]`, straight to the provider; no database). The self-hosted stack sends one to Mailpit in its smoke test. This checks the provider settings only; the whole path (queue → dispatch → send) runs on staging with the first real sender, the invitations of T-M2-07.

**Self-hosted with a real relay:** set `SMTP_URL` (and `SMTP_CA_CERT_FILE`, or set it empty for a publicly trusted certificate), remove the `mailpit` service, the worker's `depends_on: mailpit` entry and its `mail-ca.crt` mount, and give the worker a network that reaches the relay (the stack's `mail` network is internal) — see the comment in `infra/docker/compose.yaml`.

## 3. Set-up (Product Owner, once — Claude guides one step at a time)

**Deploy order:** step 1 is done **before the WP-ADM-01 pull request is merged**, so that the first worker run after the merge already publishes its key. Steps 2–4 follow the merge (and the automatic DB deploy).

1. **Before the merge — SECRET** `EMAIL_CREDENTIALS_KEY` in GitHub → Settings → Environments → **production-jobs** (a generated 64-character password; never in chat; the same value is also added in Vercel, but only for the sign-in code — [production-setup.md](production-setup.md) step 26a, ADR 0005 amendment 23 Oct 2026). [production-setup.md](production-setup.md) step 29.
2. Claude runs **Actions → Jobs** (`pass`): the worker publishes its key.
3. The Super Admin opens **Platform settings → Email** in the product: provider (e.g. Resend), its key, sender address on the verified domain, sender name, the address for the test → **Save and send test**. After the next worker pass (≤ 5 minutes; or Claude runs Jobs) the page shows «Working» — the sender is verified and waiting e-mails go out.
4. Optional, per organization: its Organization Admin opens **Settings → Email integration**, saves its provider, **Send test e-mail**, then switches on «Use my provider».

The old variables `EMAIL_PROVIDER`, `EMAIL_FROM_NAME`, `EMAIL_FROM_ADDRESS`, `RESEND_API_KEY`, `EMAIL_TEST_TO` are not read from GitHub any more (jobs.yml passes `EMAIL_PROVIDER=none`); delete them from `production-jobs` / `staging-jobs` if they are still there. The worker's `test-email` mode stays for self-hosted installation senders only.

## 4. Operations

| Situation | What to do |
|---|---|
| Platform sender failures (Super Admin page: failed deliveries of the last 24 hours) | Check the provider's account (key, domain, sending limits) and the sender settings; save and send a test again |
| E-mails wait (Super Admin warning) | No verified sender: set and test the platform sender (or the organization enables its own provider). With `CREDENTIALS_UNAVAILABLE`: enter the saved secret again (a new worker key) |
| A message did not arrive | As the database owner (SQL editor): `select status, error_code, attempts, provider_message_id, created_at from platform.message_deliveries where destination_masked like 'x***@%' order by created_at desc` — then look up `provider_message_id` in the Resend dashboard (bounces, spam complaints) |
| Many `PROVIDER_AUTH` codes | The API key is wrong, revoked or lacks sending access, or the sending domain is not verified / `EMAIL_FROM_ADDRESS` is not on it (Resend → Domains): fix it; waiting messages go out on their next attempt (within about 3.5 hours) |
| `INVALID_IDEMPOTENT_REQUEST` | The same delivery was sent before with different content (the sender settings changed between attempts): it may have arrived — check `provider_message_id`-less rows against the Resend dashboard before re-sending |
| `TENANT_INACTIVE` | The organization was suspended or closed before the message went out; nothing to do (not replayed) |
| `DELIVERY_ERROR` | The last attempt failed on the database, not at the provider — the message may still have gone out: check the Resend dashboard (or the relay's log) and the worker logs at that time before triggering it again |
| `VALIDATION_ERROR` / `ADDRESS_REJECTED` | The address or message was refused for good; correct the person's e-mail and trigger the message again (e.g. resend the invitation) |
